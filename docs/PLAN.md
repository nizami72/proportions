# План реализации: "Пропорции"

Проект пока пустой (только `docs/TZ.md`), план — с нуля.

## 1. Стек и структура проекта

- Kotlin + Jetpack Compose, минимальный SDK 26 (Android 8.0), Material 3.
- Архитектура: MVVM — `ViewModel` + `StateFlow` на экран, без лишних слоёв (DDD/Clean Architecture избыточны для этого объёма).
- Room DB (одна БД, три таблицы).
- Compose Navigation (3 маршрута: список, карточка, about).
- DI не нужен (Hilt избыточен для 3 экранов) — простая ручная фабрика `ViewModel` через `AppContainer`/`Application` класс.
- Billing: `com.android.billingclient:billing-ktx` для разовой покупки.

Модули — один `:app`, без multi-module (не оправдано объёмом).

## 2. Модель данных (Room)

```
RecipeEntity(id, name, photoUri: String?, notes: String?, createdAt)
IngredientLineEntity(id, recipeId FK, name: String, baselineAmount: Double, position: Int)
IngredientNameEntity(name PK, useCount: Int)  -- для автодополнения
```

- `IngredientLineEntity.baselineAmount` — это и есть "исходное" значение из п. 3.2 ТЗ.
- `position` — порядок строк в карточке (drag/добавление в конец).
- DAO: `RecipeDao` (CRUD + `Flow<List<RecipeWithLines>>` для главного экрана), `IngredientNameDao` (upsert + инкремент счётчика, запрос top-N по частоте с `LIKE` для фильтрации по вводу).

## 3. Ядро пересчёта — решение открытого вопроса из п. 3.2

Проблема из ТЗ: если менять поля "по цепочке" и молча перезаписывать baseline, пользователь быстро потеряет исходные пропорции из-за накопления округлений и путаницы, что является "истинными" числами.

**Решение:**
- Экран карточки имеет два набора чисел в памяти `ViewModel`, но одно поле ввода на строку:
  - `baseline: Map<lineId, Double>` — то, что лежит в Room, не трогается при обычном вводе;
  - `displayed: Map<lineId, Double>` — то, что видит и печатает пользователь.
- При правке поля `i`: `coeff = displayed[i] / baseline[i]`, затем `displayed[j] = baseline[j] * coeff` для всех `j`. Если `baseline[i] == 0`, поле блокируется как база пересчёта (нельзя делить на 0 — просто не пересчитываем, коэффициент не определён), сигнал в UI ("нулевое количество нельзя использовать как основу").
- Экран визуально помечает: пока `displayed != baseline` (есть неспасённый пересчёт) — показывается плашка/чип "Пересчитано ×N.NN — не сохранено" и кнопка **"Пересохранить с этими значениями"** (перезаписывает `baseline` = `displayed` в БД). Кнопка "Сохранить" (при создании) и "Пересохранить" (при пересчёте) — это один и тот же метод `ViewModel`, разный текст по режиму.
- Уход с экрана без пересохранения **не** трогает БД — при повторном входе снова видно исходный baseline. Это прямо снимает риск, описанный в ТЗ.
- Округление: отображение до сотых (`"%.2f"`), хранение — `Double` без округления внутри (округление только на слое форматирования, чтобы не копить ошибку при последовательных пересчётах в рамках одной сессии экрана).

## 4. Экраны

1. **Главный экран** (`HomeScreen`)
   - `LazyColumn` карточек: миниатюра (если есть `photoUri`, иначе плейсхолдер-иконка) + имя.
   - Пустое состояние: иллюстрация/текст + стрелка на FAB при `recipes.isEmpty()`.
   - FAB "Добавить" → навигация на карточку в режиме создания (`recipeId = null`).
   - Клик по карточке → карточка в режиме редактирования/пересчёта (`recipeId = id`).
   - Long-press/меню → удаление (с подтверждением).
   - Если превышен лимит бесплатных карточек (3) и нет покупки — по клику на FAB показываем paywall-диалог вместо создания.

2. **Карточка рецепта** (`RecipeCardScreen`) — один composable на оба режима (create/use), различие только в наличии `recipeId`.
   - Поле имени рецепта (`OutlinedTextField`).
   - Динамический список строк ингредиент/количество (`LazyColumn` + `IconButton` удаления на строке + кнопка "Добавить ингредиент" внизу списка).
   - Поле имени ингредиента — с автодополнением (dropdown/`ExposedDropdownMenu`, фильтр по префиксу из `IngredientNameDao`).
   - Поле количества — `TextField` с `KeyboardType.Decimal`, `onValueChange` триггерит пересчёт по формуле из п.3.
   - Кнопка "Сохранить"/"Пересохранить" (текст и активность зависят от состояния, см. п.3 выше).
   - (Опционально, после MVP) кнопка добавления фото, поле заметок.

3. **About** (`AboutScreen`)
   - Статический текст, версия приложения, ссылка на политику конфиденциальности, контакт автора (email/сайт) — `Intent.ACTION_VIEW` / `ACTION_SENDTO`.

4. **Настройки** — не в MVP, пропускаем.

Навигация: `HOME -> CARD/{recipeId?} -> (back)`, `HOME -> ABOUT`. Верхний `TopAppBar` с иконкой "About" на главном экране.

## 5. Автодополнение ингредиентов

- При сохранении карточки: для каждого уникального имени ингредиента — `INSERT ... ON CONFLICT UPDATE useCount = useCount + 1` (upsert в `IngredientNameDao`).
- Запрос для dropdown: `SELECT name FROM ingredient_names WHERE name LIKE :prefix || '%' ORDER BY useCount DESC LIMIT 10`, дебаунс на ввод не нужен — таблица маленькая, запрос дешёвый.

## 6. Монетизация

- Константа `FREE_RECIPE_LIMIT = 3`.
- `BillingViewModel`/`BillingRepository` оборачивает `BillingClient`, один `inapp`-продукт "unlock_unlimited".
- Проверка лимита — при попытке создать 4-ю карточку (после подсчёта существующих через `RecipeDao.count()`), если нет записи о покупке (хранится локально, например в `DataStore`/`SharedPreferences`, синхронизируется через `queryPurchasesAsync` при старте) — показать paywall.
- Никакой рекламы, никакого аккаунта/бэкенда — вся проверка покупки чисто через Google Play Billing on-device.

## 7. Порядок работы (файлы/коммиты)

1. Инициализация проекта (Gradle KTS, Compose, min/target SDK, зависимости: Room, Navigation-Compose, Billing-ktx).
2. Слой данных: entities, DAO, `AppDatabase`, `RecipeRepository`.
3. `HomeScreen` + `HomeViewModel` (список, пустое состояние, удаление).
4. `RecipeCardScreen` + `RecipeCardViewModel` (создание, без пересчёта).
5. Логика пересчёта в `RecipeCardViewModel` (baseline/displayed, кнопка "Пересохранить").
6. Автодополнение (`IngredientNameDao`, dropdown в UI).
7. `AboutScreen` + навигационный граф целиком.
8. Биллинг: paywall, лимит, разблокировка.
9. Полировка: пустые состояния, обработка ошибок ввода (нечисловой текст, пустое имя), тёмная/светлая тема "из коробки" через `dynamicColor`/MaterialTheme без отдельного экрана настроек.
10. Тестирование (см. п.8) → сборка релиза → листинг в Play Console.

Это соответствует оценке ТЗ (~3 дня): пункты 3-4 = UI (1д), 2+5 = логика+Room (1д), 6 = автодополнение (0.5д), 7-10 = полировка/паблиш (0.5-1д).

## 8. Тестирование

- Unit-тесты на функцию пересчёта (граничные случаи: baseline = 0, отрицательные значения запрещены на уровне ввода, один ингредиент, много ингредиентов, повторный пересчёт без пересохранения не должен дрейфовать от исходного baseline).
- Unit-тесты DAO (in-memory Room) на автодополнение (сортировка по частоте, upsert счётчика).
- Ручное тестирование UI: создание/редактирование/удаление карточки, пересчёт, лимит 3 карточек + paywall, About-экран, тёмная тема.

## 9. Публикация

- Иконка, скриншоты, короткое/полное описание под ASO-запросы из п.7 ТЗ ("ratio calculator recipe", "ingredient proportion calculator").
- Политика конфиденциальности (обязательна из-за Billing/локальных данных) — простая статическая страница, ссылка из About.
- Play Console: закрытое → открытое тестирование → продакшн.
