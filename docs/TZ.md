# Техническое задание: Android-приложение "Пропорции" (рабочее название)

## 1. Суть проекта

Минималистичный калькулятор пропорций ингредиентов. Пользователь сохраняет рецепт как набор пар "ингредиент — количество", затем при готовке меняет **любое** поле на реальное имеющееся количество — остальные пересчитываются автоматически по сохранённым исходным пропорциям.

**Отличие от конкурентов (Recipe Scaler, MealMaster, Recipe Calculator):** никакой рецептной книги — ни фото, ни шагов готовки, ни тегов, ни калорий, ни рекламы, ни аккаунта. Один инструмент, одна задача.

---

## 2. Целевая аудитория

- Домашние кулинары/кондитеры, готовящие по пропорциональным рецептурам (сиропы, тесто, маринады)
- Пользователи, которым не подходят рецептные комбайны из-за перегруженности интерфейса

## 3. Функциональные требования

### 3.1 Экраны (3, минимум 4-й опционален)

| № | Экран | Назначение |
|---|---|---|
| 1 | Главный экран | Список сохранённых карточек (имя + миниатюра-фото, если есть) + FAB "Добавить" + пустое состояние с подсказкой при первом запуске |
| 2 | Карточка рецепта | Один экран на **и создание, и использование**, но с двумя режимами для уже сохранённой карточки — см. п. 3.6. Создание нового рецепта всегда идёт в полном (Edit ratios) режиме. Верхняя панель: стрелка назад, название рецепта, компактный переключатель режима, маленькая круглая иконка сохранения (см. п. 3.6, 3.7) |
| 3 | About            |  About screen with reference to policy and contact with author |
| 4 (опц.) | Настройки | Только если понадобится: язык, тема (тёмная/светлая), экспорт/импорт базы. **Можно не делать в MVP** |

**Итого: 3 экрана для MVP**, 4 не обязателен на старте.

### 3.2 Логика пересчёта (ядро приложения)
- При создании карточки все введённые значения сохраняются как исходные (baseline) вместе друг с другом.
- При изменении любого поля на уже сохранённой карточке (в режиме "Расчёт", см. п. 3.6): `коэффициент = новое_значение / исходное_значение_этого_же_поля`, все остальные поля = `исходное_значение × коэффициент`.
- Округление: до сотых для граммов/мл (настраиваемо позже, не в MVP).
- Изменения в режиме пересчёта **не перезаписывают** сохранённый baseline автоматически — иначе следующий пересчёт снова пойдёт от старого baseline (это важно продумать в UX, иначе пользователь запутается, какие цифры "истинные"). Явной отдельной кнопки "Пересохранить" не потребовалось: используется одна и та же маленькая иконка сохранения в верхней панели (см. п. 3.6), которая **неактивна, пока сохранять нечего**, и включается, как только текущие значения на экране действительно отличаются от того, что лежит в БД (по любому полю — имя рецепта, название или количество ингредиента, добавленная/удалённая строка). Так пользователю не нужно гадать, есть ли несохранённые изменения — это сразу видно по состоянию кнопки.

### 3.3 Автодополнение ингредиентов
- Список всех когда-либо введённых названий ингредиентов, отсортированный по частоте использования.
- Хранится локально, растёт по мере использования.

### 3.4 Опционально (не в MVP, но дёшево добавить позже)
- Фото карточки (для узнавания вместо чтения имени) — из галереи или камеры, хранится локально.
- Свободное текстовое поле "заметки" — без структуры, без шагов/таймеров.

### 3.5 Дискретные ингредиенты (штучные единицы)

**Проблема:** при пересчёте по коэффициенту непрерывные величины (граммы, мл) пересчитываются точно, но штучные ингредиенты (яйца, дольки чеснока, листья желатина и т.п.) при умножении на нецелый коэффициент дают бесполезные значения ("2.37 яйца").

**Решение:**
- При добавлении поля в карточку — переключатель **"целыми единицами"** (по умолчанию выключен).
- Внутреннее хранение значения — всегда точное (без округления), пересчёт всегда идёт от исходного baseline, не от предыдущего округлённого результата — это исключает накопление ошибки при повторных пересчётах.
- Отображение на экране для полей с включённым переключателем — округлённое целое число, с мелкой пометкой точного значения рядом (например: "2 *(точно 2.37)*").
- Тип поля ("целыми единицами" вкл/выкл) запоминается для каждого названия ингредиента в автодополнении — при повторном использовании того же имени переключатель предустанавливается по последнему выбору.

**Не в MVP, но заложить как возможное расширение:** подсказка "взвесить дробную часть" — рекомендация взвесить один штучный ингредиент целиком и отмерить нужную дробную долю по весу для тех, кому нужна повышенная точность.

### 3.6 Два режима работы с карточкой: "Расчёт" и "Редактирование пропорций"

**Проблема:** логика п. 3.2 (изменение поля пересчитывает все остальные по коэффициенту) правильна для готовки "на сейчас", но мешает, когда пользователь:
- ошибся при вводе исходного значения и хочет просто исправить одно число, не трогая остальные;
- сознательно меняет сам рецепт (например, увеличивает долю сахара для нового варианта) — здесь пересчёт остальных полей от старого baseline не нужен и даже вреден.

**Решение:** на карточке рецепта — переключатель между двумя режимами. Разница между режимами — не только в логике пересчёта, но и в том, что вообще можно редактировать:

- **Режим "Расчёт" (по умолчанию для уже сохранённой карточки)** — минимальный "рабочий" вид для готовки: название рецепта и названия ингредиентов показаны как обычный текст (не поля ввода), **редактируется только количество**; кнопок "удалить строку" и "+ добавить ингредиент" нет вообще — их незачем показывать, когда состав рецепта не меняется. Правка любого поля количества пересчитывает остальные по коэффициенту от сохранённого baseline (логика п. 3.2).
- **Режим "Редактирование пропорций"** — полный редактор рецепта: название рецепта, названия и количества ингредиентов — все поля редактируемые, можно добавлять и удалять строки. Правка количества меняет **только это поле**, остальные значения не пересчитываются и не трогаются — это прямое редактирование, а не пересчёт "на сейчас".

Сохранение в режиме "Редактирование пропорций" всегда становится новым baseline напрямую (без применения коэффициента) — здесь нет разницы в поведении кнопки сохранения между этим режимом и "Пересохранить с новыми значениями" из п. 3.2, это просто обновление рецепта.

Для нового (ещё не сохранённого) рецепта режимов нет — создание всегда идёт в полном наборе полей, как в "Редактировании пропорций" (иначе создать рецепт с нуля было бы невозможно).

Переключатель режима должен быть заметным (не спрятан в меню), но при этом предельно компактным — никакого поясняющего абзаца текста рядом не нужно: сам факт того, что поля названий и кнопки добавления/удаления появляются или исчезают, уже однозначно показывает, в каком режиме находится пользователь. Решение: маленький `Switch` прямо в верхней панели рядом с названием рецепта, с однословными подписями по бокам ("Use" / "Edit") — этого достаточно, чтобы не перепутать режимы, не перегружая экран.

### 3.7 Ввод количества: своя цифровая клавиатура вместо системной

Поле "Amount" — единственное поле, которое редактируется в обоих режимах, и редактируется чаще всего (это основной сценарий использования приложения). Системная экранная клавиатура Android разворачивается на половину экрана и на телефонах с длинным списком ингредиентов закрывает именно ту часть списка, где нужно видеть результат пересчёта остальных строк.

**Решение:** поле "Amount" — `readOnly` для системной клавиатуры (фокус получает, но `IME` не вызывает). Вместо системной клавиатуры при фокусе на поле снизу экрана появляется собственная компактная цифровая клавиатура приложения: цифры 0–9, точка, забой, кнопка "Done". Она занимает меньше места, чем полноценная системная QWERTY-раскладка, и содержит только то, что нужно для ввода количества. Список ингредиентов при этом ужимается ровно настолько, насколько нужно, и та строка, которую редактируют, автоматически остаётся видна над клавиатурой (актуально при 6+ строках в рецепте).

При фокусе на поле "Amount" всё его текущее значение выделяется целиком — первая же нажатая цифра заменяет старое число, а не дописывается к нему (стандартное поведение для полей "количество", избавляет от лишнего нажатия "стереть всё").

## 4. Нефункциональные требования

- Платформа: Android, **Kotlin + Jetpack Compose** (Kotlin — предпочтительнее Java для нового проекта, у Google приоритет именно на него, Compose даёт готовый динамический список без ручной работы с RecyclerView)
- Хранение — локально, **Room DB**, без обязательной регистрации, без интернета вообще
- Целевые устройства: Android 8.0+

## 5. Монетизация

- Фримиум: 3 бесплатные сохранённые карточки, дальше — **разовая покупка** снятия лимита (не подписка — категория не оправдывает ежемесячный биллинг при таком объёме функциональности)

- Ориентировочная цена разблокировки: $1.99-3.99 разово
